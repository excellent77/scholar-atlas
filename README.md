# Scholar Atlas v2｜原文教授研究整理器

為海外研究所申請建立一個可回查原文的教授文獻庫。此版本已完全移除範例教授、預填論文與模板式的研究概要。

## 三個實作核心

1. **實體資料夾**：透過桌面版 Chrome／Edge 的 File System Access API，在使用者選定的位置為每位教授建立獨立目錄，保存個人資料、來源、PDF 與分析結果。
2. **原文分析**：以 PDF.js 在本機逐頁擷取文字，再由 Gemini API 分段分析研究問題、方法、成果與限制。每則引用都會與指定頁面的原文片段比對，並可一鍵跳到對應的 PDF 頁碼回查。
3. **跨論文概要**：選取至少兩篇已分析的論文，歸納研究主軸、演進脈絡、共同方法與申請關聯；內容區分原文整理與推論，並保留引文。

## 開始使用

1. 以桌面版 Chrome 或 Edge，在頂層分頁開啟網站（須為 HTTPS 或 localhost）。若 Safari、Firefox 不支援 `showDirectoryPicker`，就無法使用這個實體目錄版本。
2. 點選「選取電腦資料夾」，選擇一個用來存放研究資料的父目錄，網站會自動在其中建立 `scholar-atlas-data`。
3. 新增教授，填寫基本資料與官方頁面；接著新增論文並上傳有權保存的 PDF，同時確認該教授為作者之一。
4. 檢查擷取出的文字。只有來源連結、未附 PDF 的項目無法執行原文分析。
5. 到「分析模型設定」輸入自己的 Gemini API key，驗證後選擇帳戶可用的模型，也可以按「測試一次生成連線」確認。Key 只存在分頁記憶體中，重新整理頁面後須重新輸入。
6. 點選「分析原文」，並確認同意將文字傳送至 Google Gemini、使用自己的額度。完成後逐則點選引用回查。
7. 至少兩篇分析完成後，到「跨論文概要」選取論文並執行分析。研究方向需先在教授庫首頁設定。
8. 每次重新開啟網站時，選取同一個父目錄即可讀取磁碟上的資料。也可以將教授的完整資料匯出為 ZIP 備份。

API key 可在 https://aistudio.google.com/apikey 管理。請注意，ChatGPT 訂閱並不等同於 Gemini API 額度。沒有 key 時，仍可建立教授、保存 PDF、擷取文字與閱讀原文，只是無法產生模型分析。

## 原文與模型限制

- PDF 上限為 50 MB／500 頁。掃描檔須事先完成 OCR；系統不會假裝讀懂沒有可擷取文字的圖片。
- 擷取文字不等於理解圖表或公式，雙欄排版也可能打亂閱讀順序。頁碼指的是 PDF 的第幾頁，而非印刷頁碼。
- 每個片段都必須處理完成，任何失敗都不會被存成完整分析；付費呼叫不會自動重試。
- 跨論文分析最多選取 20 篇，傳送資料上限為 180,000 字元；超過上限時會直接提示，不會默默截斷。
- 原文片段核對無誤，不代表結論正確。模型仍可能誤解上下文，使用者應自行核對語意。
- 系統不會自動爬取教授名單、繞過付費牆或自動寄信，介面上也不放這些功能的假按鈕。
- 教授、論文、PDF 與分析結果都存放在本機。只有在使用者明確確認分析後，才會把文字與引用傳送到 Google；金鑰不會寫入磁碟，也不會上傳 GitHub。

## 開發與部署

需要 Node.js >=22.13。

```bash
npm ci
npm run build
npm test
python3 -m http.server 8000 --directory dist
```

`build` 會將鎖定版本的 PDF.js（含授權檔案、字碼表與字型）從 `node_modules` 複製到 `dist/vendor`。原始碼 ZIP 不包含 `node_modules`、`vendor`、私人 PDF 或使用者資料，因此解壓縮後不能直接雙擊 HTML 開啟，必須先安裝並執行 build，或改用 GitHub Actions。

部署到 GitHub 時，將專案內容上傳至 Repository 根目錄，包括 `package-lock.json`、`scripts`、`tests`、`dist`、`docs`、`AGENTS.md` 與 `.github/workflows/pages.yml`。接著在 Settings → Pages → Source 選擇 GitHub Actions。Workflow 會依序執行 `npm ci`、build、test，最後部署 `dist`。若先前已上傳 v1，請刪除舊的 `dist/seed.js`，並覆蓋所有同名檔案，尤其是 workflow 與 `package.json`。

## 實測界線

測試內容包括：以真實的兩頁 PDF 擷取文字、在實際的暫存磁碟目錄中寫入／重新開啟／封存、引文核對、長頁面的完整分段、拒絕錯誤頁碼、跨論文來源數量，以及 API 配額錯誤與輸出截斷。模型傳輸測試使用明確標示的 mock，因此不能據此宣稱 Gemini 已實測成功。部署環境未提供 API key；第一次使用時，使用者需自行執行生成連線測試，再用自己的論文測試。

## 作業規則

`AGENTS.md` 定義了專案目的、頁面與模組、命名方式、資料契約、來源標註、金鑰處理、錯誤狀態與擴充流程。例如新增「方法比較」頁時，可以重用 Claim 與 PDF 回查功能，不必另建論文模型。`SUBMISSION.md` 提供作業簡介與繳交項目，其中的身分資料與 GitHub 網址需填入實際值。

## v2.1 教授資料夾批次匯入

在首頁按「匯入教授資料夾」，選取一位教授的目錄（可包含子目錄），確認教授名稱、作者身分與保存權後即可開始。PDF 會逐篇擷取並寫入研究庫。資料夾名稱與檔名只是可編輯的預設值，並非 AI 辨識出的姓名或論文標題；學校、年份與研究方向則不做猜測。

若尚未開啟研究庫，系統會在所選目錄內建立 `scholar-atlas-data`；若已開啟，則存入目前的研究庫。姓名相同的教授須經確認才會合併，內容相同的 PDF 則依 SHA256 判斷後略過。最多可匯入 500 份，每份上限 50 MB／500 頁。非 PDF 檔案、隱藏目錄、`scholar-atlas-data` 與 `trash` 都不會被掃描。中途取消時，已成功匯入的檔案會保留，並列出尚未處理的項目。系統也不會把掃描檔當作已完成 OCR。

下次使用時，按「開啟既有研究庫」，選取原本的父目錄或 `scholar-atlas-data` 本身即可。原始 PDF 不會被移動或刪除；批次匯入也不會呼叫 Gemini，AI 分析仍需要金鑰並經過傳送確認。

新增的 `dist/folder-import.js` 負責掃描與匯入。build 時會為本機的 JS 相依模組與 CSS 加上內容版本參數，降低更新後混用舊快取的風險；網站也不會在使用中自動重新整理，以免遺失尚未儲存的輸入與記憶體中的金鑰。

## v2.2 引導流程與 API 使用

作業並未要求繳交開發者的 API 金鑰，因此本專案採用「使用者自備 Gemini 金鑰」的方式：匯入、閱讀、編輯、筆記、匯出，以及查看已儲存的分析都不需要金鑰；只有產生新的論文分析與研究概要時才需要。金鑰不得上傳到 GitHub、附在作業中，或包進任何下載檔案。

首頁分為「匯入一位教授的資料夾」與「開啟既有研究庫」兩個入口。教授頁會依 PDF、模型與分析狀態提示下一步，相關邏輯位於 `dist/workflow.js`。設定頁會保留目前所在的教授頁面，並提供返回按鈕。

批次分析只處理尚未成功分析的 PDF：開始前會一次列出完整的傳送清單請使用者確認，之後逐篇保存結果。遇到失敗時會停止後續呼叫、不自動重試，並列出成功、失敗與未處理的項目。分析完成後仍需人工核對語意，不能把「分析完成」解讀為結論必然正確。

研究概要頁可以直接編輯並儲存申請方向，勾選至少兩篇已分析的論文後即可生成。日後新增的頁面應沿用這些操作規則；新增功能時也必須保留目前所在的教授頁面與返回路徑。

課堂展示時，可以先示範不需金鑰的匯入與閱讀功能；分析功能則由操作者在自己的電腦上輸入金鑰後展示。不得提供共用金鑰或假的分析結果。
